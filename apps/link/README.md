# Electra Link

The third program in `apps/`, beside the demo and the controller. It turns an
Electra One mk1 into a second panel for an Electra One mk2: the mk1 shows a
page of a preset running on the mk2 and its knobs drive that preset. The mk1
holds no preset, no parameter values of its own, no Lua state and no router,
and decides nothing - every pixel on it is something the mk2 asked for, and
every knob turn is a request the mk2 grants.

It is the mk2's satellite program (`satellite/` in firmware-mk2, protocol in
`developers/satellitelink.md` there) on this hardware, and the two are
functionally the same thing: the same protocol, the same shared sources
(`src/Link/` is byte for byte the mk2's), the same rules about who decides
what. What differs is only what the machine underneath is.

## Building and running

```bash
make APPPATH=apps/link BUILDDIR=build-link hex
```

Add `SD_FORCE_1BIT_BUS=1` on the bench unit whose card only mounts in 1-bit
mode, as for the controller. Flash `build-link/firmware.hex` the usual way.

Plug the mk1's USB device port into the mk2's USB host socket. Nothing to
configure: the mk1 says hello on its CTRL cable every two seconds until the
mk2 answers, and the mk2 then sends it the page the mk2 is showing. The screen
says `ELECTRA LINK - waiting for a primary` until then, and a line of counters
under it - messages in and out, missed pings, hellos, dropped messages - so a
link that looks alive can be told from one that is.

## What it does

| Where | What |
| --- | --- |
| `LinkApp` | the application: enables the inbox, raises the USB read budget, runs the program from a 1 ms task, answers a bench's screenshot and file requests |
| `LinkProgram` | being a satellite: hello until answered, take what arrived, draw a view when one is complete, keep the status line true. A port of the mk2's `SatelliteProgram` |
| `LinkPageView` | the page, built from the controller's own control components inside an empty `Preset` whose pools hold the values - so the second screen is the same picture by construction |
| `LinkSurface` | the knobs: which element a knob drives (the one in the active control set first), and what a turn or a touch of it sends |
| `LinkNavigation` | the mk1's own buttons: pages, presets and control sets, and nothing else |
| `LinkSelections` | the page and preset choosers, on the controller's `Selection` and `PopupWindow` |
| `LinkWindow` | the screen, the holding message, and the twelve knob listeners |
| `LinkCustomControl` | a custom control drawn by replaying the paint the mk2 captured from its Lua |
| `LinkTransport` | one link message out on the USB device CTRL cable, framed in main memory |
| `LinkDelegate.h` | the controller's `MainDelegate` answered by doing nothing; generated by `tools/link/gen_delegate.py` |

## The panel

The mk1 idiom, because that is the panel these buttons are on. Only what
concerns pages and presets; snapshots, patch requests, the USB host window and
sleep are the controller's and a second screen has none of them.

| Button | On the page | In the page chooser | In the preset chooser |
| --- | --- | --- | --- |
| left top / middle / bottom | knobs drive row 1 / 2 / 3 | the same | the same |
| right top | - | - | - |
| right middle | presets | presets | close |
| right bottom | pages | close | pages |

An item in a chooser is picked by touching the knob under it. Holding the
pages button while picking keeps the chooser up, as on the controller, so
several pages can be looked at in one go. A preset that is neither running nor
pinned on the mk2 is drawn disabled - the mk2 refuses to show one.

The rows are the control set request of protocol version 8: the mk1's page is
its own, and so is the row its knobs drive, so the two panels can work two rows
of one page at once. Touching a knob draws the line under its control, as the
controller does; a finger on the screen moves a control and the move is sent
to the mk2, which answers with where the value ended up.

## How a message gets in

The controller assembles every SysEx on its CTRL cable into the pool in the
display's SDRAM, on the far side of the SPI bus, from the MIDI interrupt - and
skips reading altogether while the main loop is drawing, because two owners of
that bus at once corrupt the picture. That stalls the whole port for as long
as a page takes to draw, which a computer forgives and a primary driving a
satellite does not: its host port fills, the sends behind it wait, and what
could not be sent is gone - an element that never arrives is a view that never
completes.

So link messages never go near the pool. `SysexHandlerCtrl` recognises the
link command byte on the first packet and puts the message into `LinkInbox`, a
ring in main memory that the program drains on its own task. With the inbox up
the interrupt reads the USB device port through repaints and file transfers,
and the twenty-four reads it may take per tick - up from four - empty a burst
before the primary has to wait. A message that is not a link message and
arrives while the display's bus is busy is kept in main memory and handled
from the main loop as if it had arrived then; one that does not fit, or comes
while another is waiting, is refused and counted.

The link's own messages leave from `LinkTransport`, framed in a buffer in main
memory and handed to the USB stack in one call.

## Values

The mk2 sends values in the display domain. The controller's components read
MIDI values back through their message, so each value here gets a `virt`
message shaped for the translation to be the identity - a range from zero,
offset by the minimum; a list keeps the item's value, which is what its
overlay is indexed by; a pad keeps one or nought. A label the mk2 sends - an
overlay's word, a formatter's text - is the value's label, as on the
controller. Nothing is ever sent by these messages: the parameter map is this
program's store and nothing else.

## Bench

`make ... OPTIONS="-Wno-deprecated-declarations -DLINK_BENCH=1"` builds in a
handful of variables the panel can be driven through over J-Link - a button
press, a knob turn, a finger on a knob - and counters for what the link is
doing. `tools/link/` has nothing else; the mk2 repository's `developers/`
directory has the protocol and the bench recipes.

A unit in the mk2's host socket cannot be reached from a computer directly.
Add a route on the mk2 from its USB device port 2 to its USB host port 1 and
send Electra requests on the mk2's `Electra Port 2`, reading the answers on
`Electra Port 1`: the mk2 answers its own copy of every request on port 2,
which is why the two have to differ.
